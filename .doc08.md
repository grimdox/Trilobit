# Trilobit: Design Document v0.8

Oct 13, 2026 · @Eric

We build the game as a total-conversion mod on top of the stable release of Cataclysm: DDA (0.I), editing its JSON data first and its C++ only where the data cannot reach, so you can playtest within days instead of waiting on a compiler.

## Vision

You play a "ghost" (a mind) who can be moved between "shells" (bodies, increasingly synthetic) in a vertical megacity run by corporations, clans and drifters. You choose between shooting and hacking with nanohacks as your main way to fight, and between stealth and open combat. The world is open like CDDA's: take jobs from terminals and faction contacts, earn money, and work toward a way out. It plays like a classic roguelike (turn-based, permadeath, terminal display) with CDDA's tactical depth underneath.

**Working title:** Trilobit.

**What we borrow, as themes only:**

- From Ghost in the Shell: the question of what makes you *you* when your body is replaceable, cyberbrains that can be hacked, and a security-state backdrop.
- From Anarchy Online: a three-way faction struggle, implants and nanohacks as the build system, profession-style character classes, a rare resource that powers the technology, and mission terminals.

**Design pillars:**

1. **Many ways to fight.** Multiple guns, blades, nanohacks and cyberware change how you play, not just your numbers. Shooter and hacker builds are equally strong.
2. **Stealth or open combat.** Sneaking past, disabling quietly and fighting loud are all real options, and each has costs.
3. **Death is permanent, but ghosts move.** Your ghost can transfer to another body that has a cyberbrain.
4. **Staying human is a choice.** Fully human characters can't be hacked or located through the network, but they get no cyberware and face mostly pitfalls.
5. **An open world with a way out.** Survive, earn money and escape: a high-rise apartment, or a ticket out of the country or off-planet. The ending depends on your background and choices.
6. **Two cities in one.** Gleaming high-rises above and street-level scum below; gritty, with stylized touches.

## Foundation: a JSON-first CDDA conversion

CDDA is mostly data, not code, so a total conversion can be built largely by replacing data files. I checked the stable 0.I-1 source (the development branch differs in places and is not used) to confirm this before recommending it.

| Fact from the repo | Why it matters |
| --- | --- |
| About 6,200 JSON data files | Items, monsters, maps, professions and missions are all data we can replace without compiling. |
| About 565,000 lines of C++ in `src/` | Too large to rewrite; we touch it only when data cannot do the job. |
| `data/mods/` holds 40+ mods, including a total conversion (Aftershock: Exoplanet, category `total_conversion`) | Proof the engine supports replacing the whole setting, and a working template to copy. |
| `MONSTER_BLACKLIST` entries can remove monsters and whole species | We can delete zombies, wildlife and fungus in one file. |
| A JSON scripting system called effects on condition (EOCs), with about 40 data files | Lets us script events and abilities without C++. |
| Bionics defined in `data/json/bionics.json` (about 130 entries) plus a spell system for nanohacks | Cyberware and nanohacks map onto systems that already exist. |
| Terminal (curses) and graphical builds both exist | Terminal builds are supported in the source. Whether stock Windows downloads include one is unconfirmed; the fallback is building it ourselves or running the Linux version through WSL. |

**Recommended path:**

1. **Phase A, mod on a stock release.** Build our mod as a folder inside a normal CDDA download. No compiler needed; you can playtest on Windows right away.
2. **Phase B, fork with C++ changes.** Move to a fork of the source only when a feature needs code (a deeper hacking interface, new UI). Windows builds can come from GitHub Actions, since CDDA's own workflows already build Windows targets.

This keeps your fork plan, but delays the hard part until we know what truly needs it. (Status 2026-10-12: Phase B is under way; the fork builds a Windows exe on every code push and a small mod-only zip on every data push.)

## Expansion plans (added 2026-10-12)

These sections turn your 2026-10-12 notes into work Claude can pick up without waiting for answers. How the unattended work runs:

- **Defaults rule.** Every open point has a stated default (marked *Default*). Claude builds with the default unless you have changed it here. Change a default by editing the line.
- **Data first, code second.** Each item says what the 0.I-1 engine can do from JSON and what needs C++. Code-only items are built after the data parts so the game stays playable.
- **Every step ends the same way:** validate the data (including a real world load, since the check script misses math errors), commit, push, and add one line to the work log at the end of this section. The mod-only zip updates in about a minute; code changes also trigger the Windows build.
- **Claude stops and asks only for** irreversible choices (deleting content, renaming ids already in saves) and for anything marked *Needs Eric*.
- **Names.** All names here are working names. Display names live in one place per faction and NPC class, so a rename is a data edit.

### Engine facts behind these plans

Checked in the 0.I-1 source and data on 2026-10-12:

NPCs that are far from the player move only coarsely. Time-of-day conditions exist; the exact syntax is verified when the first routine is built. |
| Can NPCs drive vehicles? | No. NPCs can be passengers and avoid vehicles, but the NPC AI has no driving action. The player has an autodrive system (`vehicle_autodrive.cpp`) that could be reused. See Vehicles. |

We reuse that method for the Net (section D). |
| Can data rename an NPC to an exact name? | No `set_name` effect exists. Random names come from name lists. An exact-list assignment needs a small C++ effect. |
| Can data change faction opinion of the player? | Trust yes (`u_add_faction_trust`); making one NPC angry yes. Setting a faction's like/respect values directly, or recomputing attitudes from a rank, likely needs a small C++ effect. |
| Can the player take over another body? | Yes, `take_control` exists. What carries over is decided by us (see The Net). |
| Can data add or remove a spell (nanohack) at runtime? | There is no learn-spell or forget-spell effect in 0.I-1's effects (only `u_cast_spell`). Spells are granted by traits (a trait can list the spells it teaches, as in the bundled Aftershock and Mind Over Matter mods) or by spell-book items. So "install a nanohack" is done by adding a trait, and "remove" by removing it. The mod's 14 existing spells (`data/mods/trilobit/nanos.json`) are currently gated by a `MACHINE_BRAIN` flag and cast from the one existing `trl_bio_cyberbrain` implant. |
| Do guns have a maker or country in the data? | No. The item data has no manufacturer field, so the Russia/China/Japan/America filter is a hand-made list of gun ids, checked against each gun's real-world maker. |
| Which melee weapons already exist? | Katana, wakizashi, tanto, nodachi, naginata, bokken (each with "inferior" and "fake" variants and several forged grades), javelins, and a ninja outfit set. No kama, yari, nunchaku, throwing star or kunai. Bows exist in `data/json/items/ranged/archery.json`; no yumi. |
| How much "makeshift" and "broken" content is there? | In the stock data: 196 item ids contain "makeshift" or "broken", 60 recipes produce an item with "makeshift" in its id, and 225 data files mention "makeshift". Counts are for the stock game, not mods. |
| What do NPCs do when far away? | `overmap_npc_move` walks NPCs that have a travel goal one overmap tile at a time even when their tile is not loaded, and a new `overmap` flag on `u_run_npc_eocs` (added to the fork) runs an EOC on every NPC in the overmap, loaded or not. Routines run on that. |
| How do NPCs go to a place? | A new fork effect `u_go_to_loc` sets a travel goal and path, or a guard position when already there. |
| Why were faction enemies not attacking? | `npc::move` makes a guaranteed-hostile NPC flee for a turn when its fear exceeds `10 + aggression + bravery`, and the flee state resets attitude to neutral. Combat classes get `bonus_aggression` and `bonus_bravery` in their class definition. |

### A. Households and NPC routines

**What you asked for:** generic NPCs across the city, one per house, named from the NPC names spreadsheet; classes by house tier (poor, middle, rich); a daily schedule (leave home in the morning, go to a job, come home in the evening); rich NPCs stay home and wander between rooms about hourly; gear that fits station and job.

**Spec**

- **Who spawns.** Each house tile places one resident through its mapgen (`place_npcs`). A slum tile with two shacks places two. Residents appear when the tile is generated (when the player approaches), not for the whole city at world creation: pre-filling thousands of houses would stall world generation and the save. *Default.*
- **Names.** The 10,000-name list (`names/npc_names_10000.csv`: name, origin, gender; about 70% Japanese, 15% Russian, 15% Chinese). A small C++ effect, `set_name`, takes the next unused name from the list (a world counter), matching gender, so no two residents share a name until the list is used up. Until that effect exists, residents use CDDA's random name pools. *Default.*
- **Classes (by house tier).** `trl_res_poor`, `trl_res_mid`, `trl_res_rich`, each with job variants:
  - Poor: day laborer, street vendor, scrapper, courier, dishwasher, janitor.
  - Middle: clerk, technician, nurse, teacher, shop assistant, police clerk, driver, engineer.
  - Rich: executive, owner, investor, surgeon, retired official.
- **Equipment.** One item group each for worn clothing, carried items and weapon, per tier and per job. Cash in yen: poor 0 to 300, middle 500 to 5,000, rich 20,000 and up. Cyberware odds: poor rare, middle some, rich common; a rich resident always carries a neural interface. Weapons: poor improvised or none, middle a pistol sometimes, rich a pistol and security systems in the house. (Section J removes "makeshift" items, so a poor resident's weapon is a plain tool or a cheap blade from section I, not a makeshift one.) *Default.*
- **Home and job.** At spawn the NPC stores its home location and picks a job building by searching nearby overmap tiles for a matching terrain id (the 30 function mid-rises and shops). Poor residents pick poor-appropriate sites (workshops, food courts, flophouses), middle residents offices, clinics, schools and shops.
- **Schedule (poor and middle).** Day phases: wake 06:00, leave 07:00, at work 09:00 to 17:00, leave work 17:00, home by 19:00, indoors and asleep 22:00. A recurring EOC runs the routine for NPCs near the player and sets a goal for the next phase. *Default hours; change here.*
- **Schedule (rich).** No commute. Every game hour they pick a random indoor point within 8 tiles of home and walk to it; at night they stay in the bedroom.
- **Interruptions.** An attacked or alarmed NPC drops the routine until calm for 10 minutes, then resumes. Residents killed stay dead and their house stays empty.
- **Pass/fail tests.** A resident leaves home at 07:00, is at its job tile by 10:00, is home by 20:00 (observed from a distance, or through a debug dump). A rich resident is seen in at least three different rooms over six game hours. Names are unique across a sample of 200 residents.

**Needs code:** `set_name` effect (small). Everything else is data, but routine reliability for NPCs far from the player must be tested early (Milestone 13).

**Built (2026-10-13), as it differs from the spec:** names are 10,000 merged snippets (weight 5 each) used by CDDA's own name system, so `set_name` was not needed (about 1 in 100 names repeats). Residents spawn when a house tile generates. Jobs: 19 across three tiers, generated by `trilobit-tools/gen_residents.py`. A global recurring EOC runs every 15 to 20 minutes on all NPCs in the overmap; commuters work 07:00 to 17:00; rich residents wander within 6 tiles of home from 08:00 to 22:00; an alarmed or angry NPC pauses for 10 minutes. Cash: poor 0 to 300, middle 200 to 2,000, rich 3,000 to 12,000 yen.

### B. Vehicles and mechs

**B1. Futuristic vehicles in the city**

### D. The Net

**Intent.** An artificial place you travel to by jacking in at a terminal or through a "nethack" implant. It looks like a separate world, tinted neon green, teal and pink (inspired by Anarchy Online's net, as a theme only). It is a world within the world: outside the physical city of buildings and cars, but reached from any place in it.

**Decided (2026-10-12): the portal method, at the bottom level.**

- **How the base game does it (what we reuse).** The portal storm "dungeon" is built from existing effects, not a separate world: (1) remember where you stand (`u_location_variable`); (2) pick a location at a fixed absolute level (`z_adjust` with `z_override`, which sets the level itself and ignores your own); (3) build a room there with a map update (`mapgen_update`, using the `ERASE_ALL_BEFORE_PLACING_TERRAIN` flag); (4) teleport you in (`u_teleport`) and rename the place (`place_override`); (5) a repeating effect reruns the map update every 5 to 15 seconds so the room keeps changing; (6) an exit trap clears it and teleports you back to the remembered spot. The base game restores the old terrain on exit (`revert_location`); for the Net we skip that step, so what we build persists in the save (semi-persistent).
- **Reserved level.** **z = -10, the deepest level (the world runs from +10 down to -10), is reserved for the Net.** No other content (sewers, subways, labs, basements, caves, mission maps) may be placed at that level. This avoids the map update erasing something, and means the Net can never collide with any building, however tall.
- **Why down, not up.** The base game builds its dungeon at +6; our towers are only 5 floors tall and the world tops out at +10, so a tall building could hit a sky Net. The bottom level is always free, is dark with no sun or weather (neon terrain and furniture that emit light read as a glowing network), and needs no sky or floor.
- **Where you land.** The Net is local to where you jack in: the entry point's x and y map to the same x and y at z = -10, so the Net below a building is that building's Net. Each map update covers one overmap tile (24 by 24); a larger Net area repeats the update over neighboring tiles at the cost of generation time. Authored node maps (data havens, corporate security, a marketplace) are separate rooms reached through exit-trap style doors.
- **Look.** Our own `trl_net_*` terrain, furniture and flags in neon green, teal and pink. Colors and light emission are data. A full-screen neon filter on the graphical build needs a small code change and is optional polish. The Net's tiles are part of both tilesets (section G).
- **Your body.** The teleport moves your body to the Net. For "mind in the Net, body left behind", a stand-in body (an NPC) stays at the jack-in point so it can be found and attacked; this is possible in data but fiddly. *Default: stand-in body for implanted characters who jack in outside a safe room; none inside a safe room.*
- **Mirroring local electronics.** Showing the real world's electronics as Net objects would need a scan of the real map and a matching spawn at z = -10. Plausible in data but untested; Claude spikes it in Milestone 17 and falls back to authored nodes if it proves fragile. A code-based "net vision" view mode (the real map in neon colors, with only tagged objects selectable) remains an option for later, not the default.

**Rules (yours, with how they work)**

- **Reach.** You can interact with anything within a range of 1 tile or more. The range comes from a variable computed from your implants and nanohacks (a recurring EOC sums the relevant bionics and installed nanohacks). Base range 1.
- **Tags.** An object can be acted on only if it has both tags: `ELECTRONIC` and `NETWORKED` (JSON flags on furniture, terrain, monsters and items). People count when they carry a cyberbrain (a trait). Fully human characters are neither tag, so they cannot be seen or touched in the Net.
- **Interactions.** A menu per object type: open or lock a door, disable a camera, overload a drone, read a terminal, reroute power, steal data. Each costs energy and takes time, and may leave a trace that raises the owning faction's heat. The interactions that reach beyond your own reach range are nanohacks and follow section H.
- **Transfer (ghost).** Your ghost can move into another entity with a cyberbrain, or into another suitable storage place, using `take_control`. A **vacant shell** is a body with a cyberbrain and no mind, in a shell bank that is networked. Transfer requires a connection to the Net and a free shell.
- **What goes with you (default list, change here):**
  - Carries over: half of each skill level (rounded down), kept ghost traits, installed nanohacks (active only as far as the new shell's cyberbrain Control Value allows, section H6), the bank account, faction ranks and mission log (all stored as world variables).
  - Stays behind: the body, its implants, its hit points, its inventory, and the old body's own skills (replaced by the carried ones where higher).
- **Pass/fail tests.** Jack in from a terminal and arrive in a neon-colored room at z = -10 directly below you; the room changes while you stand in it; the exit trap returns you to the jack-in point. See at least three kinds of object, and open one door from range. Die (or choose to transfer) into a vacant shell and keep half your skills, your bank balance and your faction ranks. Confirm nothing else is generated at z = -10 in a fresh world.

**Needs code:** nothing for the first version. Optional later: the full-screen neon overlay in tiles mode, a code-based net vision, an energy-based range check if the EOC sum proves too clumsy.

### G. The tilesets: Bouma and Mokuhanga (added 2026-10-12, revised twice)

**What you asked for:** entirely new, original tilesets that overlay everything. Two of them:

- **Bouma:** the main tileset and the default. A more traditional "cyberpunk" representation, the beautiful and sometimes gritty future from your earlier brief, with Ghost in the Shell (all versions) and the city imagery of Anarchy Online as the reference points.
- **Mokuhanga:** an optional tileset. A woodblock-print look in high-contrast black, white and neon.

Both keep the resolution and level of detail of the Ultica\_iso tileset you use now.

**G0. What Ultica\_iso is (measured from `gfx/Ultica_iso` in the 0.I-1 tree)**

This is the technical spec both tilesets match.

| Property | Ultica\_iso value |
| --- | --- |
| View | Isometric (`iso: true`), `pixelscale` 1 |
| Ground tile | A diamond 48 pixels wide by 24 pixels tall |
| Level height | 108 pixels per z-level (`zlevel_height`) |
| Size 1: flat ground | 48 by 36 (floors, terrain, fields, blood, litter) |
| Size 2: low objects | 48 by 48 ("half"), 48 by 72 ("full": furniture, counters, walls) |
| Size 3: tall objects | 48 by 96 ("high": cabinets, fridges, dumpsters, wall segments), 48 by 120 and 48 by 144 ("tall", "extra tall"), plus wide variants 96 by 72 and 96 by 96 (two tiles wide) |
| Size 4: big things | 64 by 64 and 96 by 96 (large, giant), up to 200 by 240 (the "extra giant" sheet, about 470 sprites: vehicles, large furniture, big monsters) |
| Items | 32 by 32 icons (about 1,200 on the normal sheet), 20 by 20 small icons (about 1,760), guns 32 by 32, plus 2x variants 32 by 32 for big monsters and 32 by 64 for tall ones |
| Characters | `human_body_2x`: 32 by 36 sprites (about 2,650: body, hair, worn clothes, as overlays) and `human_body_plus_2x` 32 by 48 |
| Overall | 29 files, about 18 MB, about 10,000 sprite slots; a `fallback.png` and a `layering.json` file |
| Look | Clean, lightly shaded sprites with soft edges and clear silhouettes, medium detail (not tiny pixel art, not painterly); floors as flat colored diamonds with a bevel; furniture and walls as shaded boxes with readable shapes; creatures small and simple |

Both tilesets keep these sizes, offsets and sheet categories so the engine, the sprite offsets and the layering rules behave the same, and so you can swap between Bouma, Mokuhanga and Ultica\_iso in Options without anything else changing. Per-tile detail stays at this level: readable shapes first, a few well-placed highlights second, never finer than the source.

**G0a. One pipeline, two styles**

The two tilesets share all of their *shapes*: the same tile ids, sprite sizes, offsets, layout, isometric box drawing and character bodies. They differ only in *style*: palette, shading, outlines, texture and how light is drawn. Each tileset is a style file (`art/style_bouma.json`, `art/style_mokuhanga.json`) fed to the same generator scripts. Consequences:

- Bouma is built first (Milestone 19). Once its Tier 1 shapes work, Mokuhanga (Milestone 20) is mostly a new style file plus a few hand-tuned exceptions, not a second drawing job.
- A fix to a shape (a misaligned wall, a wrong offset) is made once and fixed in both.
- Hand-finished sprites (the player, landmarks, terminals, mechs) are drawn per style where the style demands it (for example, Mokuhanga's ink outlines), and fall back to the shared shape with the style applied.
- The new weapons (section I) each need an item icon (32 by 32) and, for melee and ranged weapons wielded by characters, a wielded overlay; they are added to the tier that covers items (Tier 2).

**G1. Bouma: the art brief (default tileset)**

- **Two registers, one world.** *Upper city:* clean, tall, glassy, lit from within; cool blue-white and teal light, long reflections, soft haze, orderly signage. *Street level:* wet, cramped, patched together; warm sodium amber, magenta and cyan neon against dark concrete and rust, cables overhead, steam, stacked signs, rain-slick ground. The contrast between them is the "two cities in one" pillar, shown on screen.
- **Palette.** A restrained base of deep blue-black and charcoal, with a small set of saturated accents: neon cyan, magenta, amber, and a toxic green reserved for the Net's glow and hacking effects. Accent colors are used sparingly, so a lit sign reads as a light, not as wallpaper. Each district tier gets its own accent bias (rich: cool white and teal; middle: neutral with amber; poor: magenta, amber and green on grime).
- **Beauty and grit.** Beautiful through light (glow, reflections, silhouettes, skylines); gritty through surface (grime, patches, water stains, graffiti, exposed wiring). Every tile gets at least one grit detail; only key landmarks get a beauty detail, so the grit stays believable.
- **The Net.** Its own sub-style: dark void, thin glowing grid lines, geometric neon objects, translucent surfaces. It must look clearly "not the physical city" at a glance (section D).
- **Readability first.** This is a tactical roguelike: walls, doors, floors, windows, cover and hazards must be distinguishable at a glance before they are pretty. Rule: a tile's silhouette and main color communicate its function; decoration only adds on top. Characters must stay visible against the busiest backgrounds.
- **Character look.** Fashion, cyberware and shells read from the sprite: visible implants (glowing eyes, limb plates, ports), cloaks and coats, plain clothes for civilians. NPC classes and factions get a distinct color accent so you can tell Bratva, JSDF and Nasim apart at a glance (placeholder accents: Bratva red-black, JSDF navy-white, Nasim green-violet).

**G1a. Mokuhanga: the art brief (optional tileset)**

- **The name as a style.** *Mokuhanga* is the Japanese word for woodblock printing. The look is a print: **high contrast, black, white and neon.** Surfaces are flat areas of black, white or a few light greys, separated by a thin hard line; neon is the only color, printed as flat bright ink (cyan, magenta, amber, and green for the Net) on top of the monochrome world.
- **Rules.** At most three inks per sprite (black, white, one neon), no smooth gradients (a fade is drawn as stepped bands, like a block print's bokashi), a subtle paper-grain texture on the whites, and bold outlines on silhouettes. Shadows are solid black shapes; lit windows and signs are the neon.
- **Colour meaning.** Because only neon carries color, color becomes information: the accent shows what is alive, powered or dangerous (doors that open, terminals, hostile units, the Net). Faction accents become neon hues (Bratva magenta, JSDF cyan, Nasim green) over black and white bodies.
- **Same shapes as Bouma.** Same ids, sizes, offsets and layout (G0a); only the style differs. Readability is easier here than in Bouma, so the readability rule is a pass condition, not a goal.
- **Tradeoff.** A very stylized look can hide grit and detail; Mokuhanga is meant for players who prefer contrast and clarity over atmosphere.

**G2. Reference method (and the copyright line)**

- **Use references as mood, not as material.** Claude cannot browse images from the sandbox's shell and must not copy, trace, lift or closely imitate any frame, still, poster, screenshot or game art from Ghost in the Shell (all versions: the films, the series, and the later productions) or Anarchy Online. Both tilesets must be entirely original artwork drawn by generators and by hand, with original designs, and no names, logos, characters, vehicles, signs or text from either work (the licensing rules below apply to art as much as to names).
- **What we take from the references (Bouma).** Qualities only: palette and contrast (how neon sits against dark), lighting direction (top-down haze, wet reflections), density of overhead signage and cables, building massing and the vertical stacking of the skyline, texture vocabulary (concrete, glass, steel, wet asphalt), and the contrast between sleek and shabby. Anarchy Online's city art is used mostly for the readable, painterly isometric-city feeling at street level and its grungy-future color mood. Mokuhanga takes only the same contrast and silhouette qualities, restyled as a print.
- **Ultica\_iso is a specification, not source art.** We measure its sizes and layout (G0) and nothing else. No sprite from Ultica\_iso, UltiCa, or any other bundled tileset is copied, recolored, traced or reused (their artists hold the credit and license; see the licensing section).
- **Reference boards (Eric).** Eric collects and keeps the boards in a private folder (one per mood: upper city, street level, interiors, characters, the Net), and shares them with Claude as attachments when he wants a pass tuned. Boards are never committed to the repo or released with the game. For each board Claude writes a short "extracted notes" list (palette swatches, light, density, materials) into `art/notes/` in plain words; those notes, not the images, drive the generator settings. *Needs Eric: the boards. Until they arrive Claude works from the brief in G1.*

**G3. Technical plan**

- **Format.** Standard CDDA tilesets in the same layout as Ultica\_iso: a folder per tileset, `gfx/Bouma/` and `gfx/Mokuhanga/`, each with `tileset.txt` (`NAME`, `VIEW`, `JSON: tile_config.json`, `TILESET: tiles.png`), `tile_config.json` (a `tile_info` block with width 48, height 24, `zlevel_height` 108, `iso: true`, then one `tiles-new` entry per sheet with its sprite width, height and offsets as in G0) and the PNG sheets. They load in the Windows graphical build like any bundled tileset; players pick them in Options, and Bouma is the default for the Trilobit mod. Anything with no sprite falls back to the ASCII glyph (CDDA's normal behavior), so each tileset can be delivered in stages.
- **Isometric drawing.** Everything is drawn in the same two-to-one isometric projection (a tile is a 48 by 24 diamond; a wall segment is a box rising from it). Generators use a shared `iso.py` helper: draw a box (top, left and right faces) from its footprint and height, project to the diamond, shade the faces by the active style, add the outline. This suits generator-first work well, since towers, walls, furniture and vehicles are all boxes and ramps. Because iso sprites are drawn for one view angle, objects that face a direction (furniture, vehicles) get the paired or four-way variants the engine already supports through rotation entries in `tile_config.json`.
- **Layers.** CDDA draws each map tile in layers: terrain, furniture and traps, fields and effects, items, creatures (monsters, NPCs, the player), then overlays (worn clothing, wielded items, bionics) and lighting. Our sprite ids follow the same keys (`t_` terrain, `f_` furniture, item ids, monster ids, `overlay_worn_*`, `overlay_wielded_*`, `player_*`), using the `trl_` ids the mod defines. Terrain uses the multi-tile `connects_to` feature (autotiling) so one set of walls and roads covers every map shape; the engine's `layering.json` is copied in structure (not content) from Ultica\_iso so overlays sort the same way.
- **Lighting and glow.** Neon and screens are part of the sprite art (bright "ink" or glow) rather than real light; real light comes from the game's own light sources. We add small additive "glow" overlay sprites for signs and terminals (soft in Bouma, a flat hard-edged neon shape in Mokuhanga), and tint the Net tiles green/teal/pink. A full-screen post-process (bloom, rain streaks, scanlines) would need a small code change in `sdltiles.cpp`; kept as optional polish after the tilesets are drawn (like the Net's neon filter).
- **Characters.** Eight-direction sprites for the player and every NPC and enemy class at the `human_body_2x` size (32 by 36, with the same offsets), built from a shared base body (slim, average, heavy, plus a small number of full-shell frames) with worn clothing, hair and implants as overlays, as Ultica\_iso does. The facing prototype already exposes eight facings; the facing arrow stays as a debug option. Mechs, vehicles and drones use the large and giant sheets, with rotation handled by CDDA's vehicle rotation support.
- **Pipeline (how we make the art).**
  1. **Generator first.** Python scripts in `trilobit-tools/` (like `gen_splash.py`) draw tiles with Pillow through the `iso.py` helper: floors as diamonds with grime and grain, wall and tower faces with lit and unlit windows, neon signs from a small original glyph set (simple shapes and abstract symbols only, no real text or brands), doors, furniture boxes, rain-wet ground variants. Seeded randomness keeps every build identical. Palette, ink count and rendering rules are parameters in each style file, so a mood change is a settings edit and a regenerate.
  2. **Hand-finished key sprites.** Landmarks, the player, NPC classes, terminals, mechs and the Net's signature objects are drawn or refined by hand-guided scripts (and by Eric if he wants to paint any). These override generated ones by id.
  3. **Assembly.** `trilobit-tools/build_tileset.py --style bouma|mokuhanga` packs sprites into the same sheet categories as G0 and writes `tile_config.json`; a validator checks sprite sizes against the category, every `trl_` terrain, furniture, monster and NPC id for a sprite, and lists the gaps.
  4. **Delivery.** The tilesets live in `gfx/Bouma` and `gfx/Mokuhanga`; the mod-only update zip covers `data/mods/trilobit`, `data/title` and `gfx/splash`, and will be extended to include both folders, so a tileset update ships in about a minute without rebuilding the exe. The Windows exe build, which today includes `gfx/`, gets a path filter so Ultica\_iso and other bundled sets are untouched.
- **Needs code:** nothing for working tilesets. Optional later: the post-process glow/rain/scanline layer, a Trilobit default-tileset setting (so Bouma is chosen on first run), a second font for neon signage.

### H. Nanohacks and Control Value (added 2026-10-12)

**What you asked for:** rename all nanos and hacks "nanohacks"; give each a Control Value (CV) that limits how many you can have installed and usable at once; make CV depend on the quality of your cyberbrain implant; let you remove nanohacks to free CV; and, as a stretch, make remote control of robots or people (and some implants) use CV too.

**H1. The rename**

- **Player-facing.** Every active ability that is now a "nano-program", "nano", "hack" or "nano-hack" is called a **nanohack**: menus, descriptions, item names (chips), shop text, mission text and this document. The word "hacking" stays for the *activity* of breaking into terminals and networks (terminal access, section D); the *abilities* you cast or run are nanohacks. Category prefixes stay as flavor (for example "Mend: Purge", "Ghost: Thermal Cloak"), and the menu groups them as Nanohacks.
- **In data.** Ids change from `trl_nano_*` to `trl_nh_*` (spells, effects, traits, items), the file `nanos.json` becomes `nanohacks.json`, and the profession bundle `trl_nano_suite` becomes `trl_nanohack_suite`. There are no released saves yet, so renaming ids is safe now and would not be later; Claude does it as the first step of Milestone 21 and then runs a fresh world load. *Default.*
- **Today's content.** The mod already has 14 of them (Purge, Reactive Shell, Afterimage, Lock-On, Shock Field, Thermal Cloak, Noise Dampener, Pulse Scan, Night Eye, Print Ammo, Print Bandages, Blink, Hop, Siphon), all gated on the cyberbrain.

**H2. Control Value (CV): the rule**

- **Two numbers.** *CV limit* is how much control your cyberbrain gives you. *CV used* is the sum of the CV costs of everything installed. You can install a nanohack only while CV used plus its cost is at most your CV limit.
- **Cost per nanohack.** Each nanohack has a CV cost of 1 to 6 (so "how many" depends on how strong they are): small utilities cost 1 to 2, combat and movement 3 to 4, the strongest (cloaking, blinking, area attacks) 5 to 6. *Default.*
- **Installed means usable.** Everything installed is ready to use (spending energy as now). There is no separate "loaded" state to manage, which keeps it simple.
- **Starting values (working costs for today's 14):** Night Eye 1, Purge 1, Afterimage 2, Noise Dampener 2, Pulse Scan 2, Print Bandages 2, Reactive Shell 3, Lock-On 3, Print Ammo 3, Hop 3, Shock Field 4, Siphon 4, Thermal Cloak 5, Blink 5. Tuned in play.

**H3. CV from the cyberbrain**

- **One cyberbrain, five grades.** The cyberbrain implant (`trl_bio_cyberbrain` today) becomes five grades, chosen by quality and price, each replacing the last (one cyberbrain slot, so upgrading is surgery). Working names and limits (*Default*):

| Grade | CV limit | Who has it |
| --- | --- | --- |
| Cyberbrain Mk I | 4 | Cheap street implant; starting characters |
| Cyberbrain Mk II | 8 | Common among the middle class |
| Cyberbrain Mk III | 14 | Professionals, mid-faction soldiers |
| Cyberbrain Mk IV | 22 | Rich, elites, faction specialists |
| Cyberbrain Mk V | 32 | Rare; military-grade, restricted, quest rewards |

- **How the limit is computed (data).** A recurring EOC reads which grade you have (`u_has_bionics`) and stores the limit in a variable; installed nanohacks add their cost to a second variable. A damaged or disabled cyberbrain lowers the limit (see H6). Pass: swap grades and see the limit change.
- **Fully human characters** have no cyberbrain, no limit and no nanohacks (pillar 4).

**H4. Installing and removing**

- **A nanohack is a chip.** A chip is an item you buy, loot or are paid. *Install* consumes the chip into your cyberbrain's library (it takes 10 minutes, not allowed in combat) and adds its cost to CV used. In data, "installed" is a trait the nanohack grants that teaches its spell (the bundled Aftershock and Mind Over Matter mods do this); the install action adds the trait and the cost.
- **Removal frees CV.** *Remove* (5 minutes, not in combat) deletes the trait, subtracts the cost and **returns the chip**, so swapping loadouts is free apart from time. You can remove any nanohack at any time; there is no permanent lock-in. *Default.*
- **Where.** From the cyberbrain's own menu (the implant status menu already exists in the mod), or at any terminal. *Default: anywhere out of combat.*
- **Pass/fail tests.** With a Mk I (limit 4): install a cost-3 chip, then a cost-2 chip is refused (3 + 2 is more than 4); remove the cost-3 chip, the cost-2 install succeeds and the chip is back in your inventory.
- **Implants that use CV.** Some software-heavy implants also cost CV and count against the same limit, so a fully loaded mind has to choose between implants and nanohacks. Default set (to tune): smartlink (gun sight link), reflex coprocessor, net-jack interface, wallet link, drone link. Their cost is charged when installed or switched on (data can check and refuse switching on; blocking the surgery itself needs a small code change, optional).

**H5. Stretch: remote control uses CV**

- **Idea.** Controlling a robot, a drone, a mech (section B3) or a person through the network occupies CV *for as long as the link lasts*. Free CV is the limit minus installed cost minus linked cost. A link can only start if there is enough free CV, and it breaks if free CV goes negative.
- **Working link costs:** small drone 2, combat drone 3, Kumo or other mech 5, a person (a "puppeted" NPC) 8, a vehicle 4. *Default; tune.*
- **Engine reality (an honest unknown).** `take_control` swaps your body for another for good, so it is not remote control. Remote control of a monster or a person while keeping your body needs a spike: data options (give orders to a friendly drone through a nanohack, with CV charged while the order effect runs) will probably cover drones and mechs; controlling an unwilling person needs code. *Plan: build drones and mechs first as data in Milestone 21, and report whether puppeting a person is possible in data or needs a small code change.*

**H6. Edge cases and decisions**

- **Over limit.** If your CV limit drops (cyberbrain damaged by an EMP or a hostile hack, downgrade, or a ghost transfer into a weaker shell) and CV used is now higher, the **most recently installed** nanohacks are *suspended* (inactive, still stored) until you are back within the limit; removing one frees CV immediately. Nothing is deleted. *Default.*
- **Ghost transfer (section D).** The carry-over list keeps your installed nanohacks, but they are active only as far as the new shell's CV limit allows; the rest are suspended and can be removed to chips if you can reach a free hand.
- **Enemy hacks.** A hostile nanohack can lower your CV limit for a while (a debuff), which suspends your newest nanohacks. This gives the counterplay promised in section F8.
- **Energy is separate.** CV is how many nanohacks you carry; energy is what you spend each time you run one. A big loadout does not cost energy until used.
- **NPCs.** Faction elites have a grade and a loadout of the same size rules, so enemy nanohackers are bounded the same way.

**H7. Pass/fail tests (whole section)**

- No "nano-program", "nano", "hack" (as an ability) or "nano-hack" remains in player-visible text; ids are `trl_nh_*`.
- A fresh world loads with no data errors after the rename.
- The five cyberbrain grades give limits 4, 8, 14, 22 and 32; the install, refuse and remove tests in H4 pass.
- A cyberbrain stunned or removed suspends nanohacks, and restoring it reactivates them with no loss.
- A shell swap into a Mk I from a Mk III keeps all nanohacks, activates only up to 4, and lets you remove down to the limit.
- Stretch: a drone link costs CV while linked and ends when CV is short.

**Built (2026-10-13):** `trilobit-tools/gen_nanohacks.py`. A nanohack is two traits: `trl_nh_<x>` (active, teaches the spell) and `trl_nhq_<x>` (suspended). Install is the chip's use action; the Control Value limit is the highest cyberbrain grade installed (a recalc EOC runs on every install or removal and every 30 seconds). When the limit drops, the newest nanohacks are suspended one at a time; when it rises, the oldest suspended ones wake while they fit. A nanohack console item opens the removal menu. Not built: the 10-minute install time, the in-combat block, and CV-using implants.

**H8. Needs code:** nothing for H1 to H4 and H6. Optional: a hard block on installing a CV-using implant over the limit (H4); the remote-control stretch for people (H5), to be settled by the spike.

### K. Androids: hackable working shells (added 2026-10-13)

**What you asked for:** androids that can be taken over through cyberhacks and that perform routine jobs. They have equipment and capabilities. They are a creature type that can be built on extensively.

**K1. What an android is**

- **A shell with no ghost.** An android is a synthetic body running a work program instead of a mind. It is an NPC (not a monster), so it can wear and carry equipment, follow the same routines as residents (section A), trade, talk, fight and be controlled with `take_control`. Its program is a firmware package; hacking replaces or overrides that firmware.
- **Tags.** Every android carries `ELECTRONIC` and `NETWORKED` (section D), so it is always visible and touchable to a hacker in range. It has no flesh: no hunger, thirst or sleep, and it is immune to flesh effects (bleeding, infection) but takes damage to its frame and can be disabled by electrical and EMP effects.
- **Not a resident.** Residents are people with ghosts and cyberbrains; androids are owned equipment. They live in a workplace (a shop, a bar, a factory, a depot), not a house, and are placed by that building's mapgen.
- **Vacant shells (section D).** A vacant shell is the same creature with firmware set to "empty": no routine, waiting for a ghost. Transfer into one uses `take_control`, so ghost transfer and android takeover share one mechanism.

**K2. Built from four parts (this is what makes it extensible)**

Everything is generated from tables in `trilobit-tools/gen_androids.py`, the way residents and factions are, so adding content means adding a row.

| Part | What it decides | Examples (working names) |
| --- | --- | --- |
| **Frame** (chassis) | Body stats, hit points, speed, carrying capacity, armor, base look, how many module slots | Civilian frame (light, 6 slots), Labor frame (strong, slow, 5 slots), Security frame (armored, 8 slots), Courier frame (fast, light, 4 slots), Companion frame (human-like, 6 slots), Heavy frame (large, 10 slots) |
| **Role** (job) | Routine, workplace type, hours, dialogue, default gear and item group | Porter, cleaner, shop clerk, bartender, courier, guard, medic, mechanic, data-runner, escort |
| **Modules** (equipment and capabilities) | Bionics, traits, spells and tools it carries; one list per role plus optional extras | Strength actuators, grip tools, scanner eyes, medical kit arm, shock baton, onboard gun mount, cargo bay, signal booster, cloaking skin |
| **Firmware** (behavior and security) | Routine, alert behavior, who it obeys, and how hard it is to hack | Stock (obeys owner, low security), Hardened (corp-grade, high security), Military (combat behavior), Rogue (no owner, unpredictable), Vacant (no routine) |

A finished android id is a combination, for example `trl_andr_labor_porter_stock`. Each part is its own list, so 6 frames, 10 roles and 5 firmwares make 300 variants with no extra writing, and any new part multiplies the set. Owner faction and tier (poor, middle, rich district) pick which variants appear where.

**K3. Roles and routines**

- Androids reuse the resident routine engine (section A): a home spot (their station or charging dock) and a work spot, with an hourly phase table. Differences: no commute home at night (they recharge at their dock), shifts run longer (a 16-hour day), and some are stationary (a clerk behind a counter, a guard at a post, a bartender behind a bar).
- A **recharge** state: a worker returns to its dock when its battery is low. A low battery slows it; an empty one makes it freeze until recharged, so you can run a "drain" attack on it.
- Roles map to the rest of the game: clerks and bartenders hold shops and bar services (sections C, E), guards patrol buildings and faction sites, couriers carry goods between shops, medics sell treatment, mechanics repair gear. A replaced or destroyed android is replaced by its owner after several days (unlike residents), which is a use for jobs and a cost for hacking.

**K4. Hacking and takeover**

A hacker steps through levels of control. Each level is a nanohack (section H) with its own Control Value (CV) cost, and each needs the android to be in range and tagged (section D).

| Level | Effect | Working CV | Notes |
| --- | --- | --- | --- |
| Probe | Reveals model, owner, firmware, battery, orders and module list | 1 | Silent |
| Disrupt | Freezes the android for several seconds, or crashes its routine | 2 | Silent for stock firmware, trips alarms on hardened |
| Command | Gives one order for a while: follow, guard here, attack target, open this door, fetch an item, work for me | 3 | The android obeys until the link breaks or the order ends; CV is charged while the order runs |
| Puppet | You see through and control its body while your own stays put | 5 to 8 by frame | Section H5 remote control; ends when CV runs short, the android is destroyed or you take damage |
| Own | Rewrites ownership permanently: it becomes your android with a stock routine for you | 3 to hold (a standing follower) | One-way; the previous owner may notice and hunt it |
| Jack in | Your ghost enters the android's body with `take_control` (ghost transfer) | none while inside | Needs a cyberbrain on the android (companion and security frames) or a vacant shell |

- **Security.** Each firmware has a security level that the hack must beat, using hacking skill, nanohack grade and any deck or terminal bonus (section D). A failed attempt may alert the android, its owner or nearby security, and raises the owning faction's heat. A hardened or military android may counter-hack, lowering the hacker's CV limit for a while (section H6).
- **Ownership.** Each android has an owner: a shop, a person, a building or a faction (stored as a hidden trait and a variable). Taking one that belongs to a faction lowers your rank with that faction (section E); taking an unowned rogue does not.
- **Fully human characters** cannot do any of this (pillar 4), but androids can still be bought, hired and fought.

**K5. Equipment and capabilities**

- **Equipment.** Each android has item groups for worn gear, carried tools and weapon, per role, like residents. A porter carries a hand truck and a cargo harness; a guard a baton or pistol and a vest; a medic a first-aid kit. Hacked androids keep their gear and you can change it.
- **Capabilities.** Modules grant traits, bionics or spells: strength, scanning, medical treatment, repair, onboard weapons, EMP resistance, a built-in radio (calls for help), a cargo bay (extra storage). The module list is the part a player-owned android can change at a mechanic.
- **Damage and repair.** Frames have hit points per limb, can lose limbs, and are repaired (not healed) at a mechanic or with a repair kit. A destroyed android leaves salvage: parts, a chip with its firmware (which can be copied to another android) and sometimes its modules.

**K6. Ties to the rest of the game**

- **Nanohacks and CV (H).** Every control level above is a nanohack with a CV cost; standing followers and puppets use the link cost rule in H5, so a hacker's army is capped by the cyberbrain grade.
- **The Net (D).** In the Net, androids appear as tagged objects; a network node can hold a "fleet manager" that hacks every android of one owner at once.
- **Factions (E).** Each faction runs androids: Bratva uses cheap labor and enforcer frames, JSDF security frames and police drones, Nasim hacked or rogue androids. An android of a faction counts for that faction's enemy list, and hacking one is a crime against its owner.
- **Residents and routines (A).** Same routine engine; androids are the "worker" half of a street scene beside the residents.
- **Merchants and jobs (C).** Androids staff shops and bars; shop terminals can be an android's job. A player can lease an android to work a shift for pay (a stretch tying to C2).
- **Vehicles (B).** Heavy frames and mechs (B3) share the module and puppet rules; a mech is a heavy frame with a cockpit.
- **Tilesets (G).** Each frame needs a base sprite; roles add overlays (vest, tool, cargo harness). Faction accents apply.

Routine: a battery (drops 2 per 15-20 minutes, recharges at the dock), porters roam within 8 tiles of the dock, posts stay within 3. Placed in 15 city places. Hacking: Probe (CV 1), Disrupt (CV 2) and Take Over (CV 4) are nanohacks; a stock-firmware android taken over becomes your follower (new fork effects `u_recruit_npc` and `u_dismiss_npc`); hardened firmware resists and turns on you. **K8. Pass/fail tests**

## Licensing and naming

Because you plan a public release, the game must use original names and carry CDDA's license obligations. I am not a lawyer, so treat this as a plan to confirm, not legal advice.

- **CDDA's license.** The repo's license file says Cataclysm is under Creative Commons Attribution-ShareAlike 3.0. Our game, built from it, would need to credit CDDA and be released under the same terms. Selling it is generally allowed under that license, but the share-alike rule would still apply.
- **Fonts and bundled tools** carry their own licenses (Unifont, Terminus and others); we keep their notices.
- **Ghost in the Shell and Anarchy Online are protected works.** We use them as inspiration for themes and visual mood only. No character, faction, place, term or item names from either (no corporation, planet, resource or program names from Anarchy Online; no characters, units or agencies from Ghost in the Shell), and no art, screenshots, logos or traced designs from either (section G2). The anti-materiel rifle takes only the role seen in Ghost in the Shell, not a design or name (section I3).
- **Bundled tilesets.** CDDA's own tilesets (Ultica\_iso, UndeadPeople and the rest) are separate works with their own credits, drawn by community artists. Bouma and Mokuhanga are built from scratch and use none of their sprites; only the sizes and sheet layout are matched (G0).
- **Real gun names.** The stock guns we keep from the four countries carry real model names and designs. That is acceptable for private playtesting, but a public release should rename them or replace them with the original guns in section I, because model names can be trademarks. Tracked as a release task.
- **Our own names.** Every faction, place and resource gets an original name from the start, so we never have to rename later. "Trilobit" is the chosen working title; "Bouma" and "Mokuhanga" are the tileset names (Mokuhanga is an ordinary Japanese word for woodblock printing, and Bouma is an existing word and surname, so neither is protected as a single word, but we still check for conflicts before release). The gun makers (Hoshikawa Arms, Volkov Works, Granite Arms, Longhai Ordnance) and "Cyberbrain Mk I to V" are working placeholders to check as well. The faction names Bratva, JSDF and Nasim are working placeholders (JSDF is a real organization) and are tracked for renaming before release.

## Decisions and open questions

**Decided (your answers, 2026-10-11):**

- **Name:** Trilobit.
- **Fantasy:** shooting or hacking with nanohacks is the core of combat, with many guns and many nanohacks to choose from; stealth and open combat both work. Facing and vision cones apply to the PC and to every NPC and enemy.
- **Hacking:** both modes. Nanohacks depend on your implants and cyberbrain. Terminal access (fixed terminals, portable decks and implant-based access) makes closed-circuit electronics hackable at all and makes nanohacks easier.
- **Energy:** health and energy are the two key meters. Implants and nanohacks run on energy stored in yourself and in batteries. When it runs out they stop or work worse, which is the tradeoff between spending energy on nanohacks and on strong combat implants.
- **Recharging:** keep CDDA's current methods for now. Variety and specialization come in Milestone 12.
- **Survival needs:** keep hunger, thirst and sleep for now; we may simplify or remove them later.
- **Guns:** keep CDDA's detailed mechanics but start from the Generic Guns mod. Target about 20 ammo types, not 200, with room for energy cells and caseless rounds. The proposed list is in section I2.
- **City:** scalable to a moderate city, tiled from several cities if needed. Pass mark and stretch goal are in Milestone 2.
- **Death:** permanent. Ghost transfer into any body with a working cyberbrain stays in the design, depending on hacking skill and the environment.
- **Fully human characters:** no cyberware, immune to hacking and network tracking, with mostly pitfalls.
- **Tone:** gritty, stylized in places, with a sharp contrast between high-rise and street level. Focus on cities, with some open space and fewer forests.
- **Structure:** open world like CDDA, with contracts from terminals and faction contacts.
